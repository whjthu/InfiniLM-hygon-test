# 质量与服务验收口径

2026-10-26 用户直接澄清后生效。此前记录中的 token/中间值 exact 检查继续作为历史诊断证据，不能据此单独淘汰候选。

- 前期输出应基本合理、任务答案正确，无非有限数值、越界或状态生命周期错误。文本、推理过程和输出 token 可不同。
- 后期使用相同数据、模板、精度基线、采样参数和生成预算的真实 benchmark 比较质量。报告准确率/任务得分、配对差值与区间、样本量、解析失败、截断及覆盖率。小样本无显著差异不代表已证明不掉点；双方零分不构成通过。
- GSM8K 的最终数值答案对标准答案评分，与整段生成 token 对旧实现完全一致是两回事。正式套件与自定义 0-shot/子集必须区分；不截断题干、不根据答案挑题，不把输出达到上限计为自然结束。
- 投机推理区分严格保目标分布的校正采样和允许质量近似的方案。逐步候选接受属于算法步骤，不要求整个输出等于历史 AR。记录 accepted tokens/cycle、draft/verify/rollback/commit/emit 的真实成本与状态恢复。不得以全部接受伪造加速。
- 量化必须同时测质量、显存、加载、prefill、decode、用户延迟及每卡吞吐；支持权重格式不等于原生低精度计算加速。
- 用户服务测试包括不同请求、自然 EOS、不同长度、闭环并发和开放到达。记录排队、拒绝、失败、未完成、TTFT/ITL p50/p95/p99、逐请求(n-1)/(last-first)、总输出/全部卡数与满足用户速度要求的 goodput。不得推迟首 token 时间点美化结果。
- 当前单用户 decode 目标严格 >15 tok/s；其他 SLO 尚未与用户约定，作为完整曲线报告，不自行声称已达到生产要求。

真实 benchmark 优先 GSM8K 与 MMLU/中文知识任务。首轮固定随机32题仅用于快速筛查；后续扩大样本并按任务/置信区间决定是否存在明显掉点。代码评测须使用隔离执行环境，不能直接在登录节点执行模型生成代码。
