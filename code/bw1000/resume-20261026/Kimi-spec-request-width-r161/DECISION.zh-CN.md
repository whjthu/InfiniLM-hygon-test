# Kimi 投机服务：请求级宽度预测的 CPU 判定

结论：本候选停止专用 GPU 验证，保持默认关闭；不为它增加模型加载。原实现的 W8 策略继续保留。

当前 445/449 实现已经用一次逻辑 RPC 发出真实 Torch draft batch，不是逐请求串行调用草稿模型。Native verify 仍在关键路径上。独立 C1 的 18.04 tok/s 是一次仅服务一个请求的32题汇总；C8 的38.71 tok/s和C16的45.47 tok/s是共享同一服务实例时的总速度，不能把18.04乘并发数。C8/16的单用户速度下降是实际观察，不是指标换算错误。

本次只尝试尚未覆盖的请求级宽度预测：首四次维持W8；最近四个已提交的完整W8周期中至少三次只接受0–2个proposal时缩到W4，每四次再探测一次W8；C1–C3永远W8。当前周期的未来接受结果不参与决定。原C16W4/C32W2预算规则保持。原接受规则、bonus token、状态提交和回滚不改。原有C1均匀缩W2/W4已测得更慢，因此不重复。

Root提供了449 node0的白名单记录，共12个重复case、3304个request-cycles；原报告SHA为 `d68e6f737b11ad5f6ac27e3b8304c20e318af74f65bd78801d51858705d6c7db`。这些是同32题及profile重复臂，不是96道独立题。依过去反馈选择宽度，使用当前结果只在选择之后计算同周期前缀账本：

- Native输入工作量T：26432→25280，减少 **4.36%**，低于事先规定的10%最小空间。
- 同周期可见有效前缀：19053→18448，减少 **3.18%**。
- 288次缩宽中，有193次原实际接受至少4个proposal，占 **67.01%**。过去几次低接受不能可靠预测当前周期仍低接受。
- 每有效前缀token的T：1.3873→1.3703，只有很小的计数改善。

这些不是GPU性能，也不是生成质量结果。反事实固定了原请求轨迹；一旦缩宽后bonus token改变，后续生成与状态就未被实际重演。MoE路由和Native成本对T非线性，不能把4.36%当成速度提升。真实wall、tok/s、质量均为UNKNOWN。`CPU-real449-prefix-accounting-r161.json`明确记录此边界。

当前草稿实现固定8个Transformer位置、最多7个proposal；Native每请求宽度也最多8、flattened T最多64。把参数改成16不能形成有效长草稿方案；需要另外的草稿模型/训练或多轮草稿算法及Native长块验证能力。由于C8当前多数周期接受较长前缀，降低输入工作量会直接丢掉可用候选。更有价值的方向是降低已有T64 target verify算子成本，或取得真正支持更长块的草稿；草稿RPC优化不足以解决当前较慢用户。

本包的policy和8项CPU调度合同仅保留为负结果的可复核来源，不接入当前生产默认、不提供GPU启动器。没有SSH、Slurm、Git、网络或模型执行。
