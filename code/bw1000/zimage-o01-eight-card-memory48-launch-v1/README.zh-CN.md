# O01 48 GiB 八卡见证及独立宿主 RAM 观察

当前包保留原 8 DCU、12 CPU、240 秒、见证器数值、合成 BF16 输入和 1103606.1982 Native。新实验选择 48 GiB 主机内存，以便获取混合运行实际水位。已知 .2175 申请 24 GiB 后 OOM，.2185 测得普通单进程八卡保底峰值 16540413952 B。这两项历史结果都没有测得新混合八进程峰值。

最近封存事实是 .2185 在 07:09:55 北京时间看到 .2179 仍正常占八卡，原保底预算 09:50:09 到期。根必须按实际编号确认同一保底自然终结。本包无取消路径，不能以预算或旧快照代替终态。

## 入口

    python3 -I -S -B render.py NEW_STAGE

由上次通过的 HOST 和设备源确定性渲染 23 个部署成员及清单。新版 host_run.py、guarded-standby-bridge.py 和 runtime/ 都在相同 stage。双保护 bridge 保留原 e23 请求处理，并额外保护当前新范围。没有守卫的其他入口，在同一锁和持久预约下仍须排除本节点。

transport.py 调用原已钉定传输配置，支持原 deploy、observe、reserve、pre、handoff、gpu、post、grant。根串行采用和发布，核新清单 SHA 后才能选择这些入口。本地回归只渲染、校验 stage 和执行隔离 fixture。本轮没有调用任何传输或调度。

## 次序与验收

1. 在现有保底锁内保护新范围。预约只接受原 .2179 编号和同节点实际状态。新 pre 要求原步真实 COMPLETED 0:0，并独立核相同 boot、完整八 PCI 和零持有者。
2. GPU arm 只设置一个 240 秒 epoch，先将零卡 RAM 观察写独占 intent，并等待精确 1 CPU、256 MiB、0 GRES 的实际编号。接着才允许唯一 12 CPU、48 GiB、8 DCU 步。两步均用 --exact，且不使用 --overlap。目标独立核实际 CPU affinity 无交叉，否则没有 baseline，监督器不能进入 HIP inventory。
3. 监督器原第一次设备调用前必须见到与同一 scope 绑定的真实 cgroup 限额、祖先限制和首样本 SHA。观察器在独立 cgroup 每秒写私有样本，保留冷启动、七兄弟、探针、恢复与清理阶段。目标 cgroup OOM 或消失后，已落盘内容仍可供独立核对。启动失败或计数缺档保持原状态。
4. 常规 post 要求目标该编号及观察者都已终结。确有独占的拒绝记录证明 GPU 未调用，以及观察者实际编号已终结时，可使用同一 cleanup 入口。两种结果都有明确字段。只凭 SSH、目录缺失或 Slurm 暂时无行不能认定原尝试未发，也不会复播。之后由原保底逻辑对新范围取得独立清场和八卡两点增长。

实卡前仍需现场验证两个独立步骤实际可共驻、CPU 集合不重叠、48 GiB 限额以及空闲节点可用性。零卡内部计数不能证明 HBM 或算子吞吐。
