# O01 同流 D2H 分块对照

原重叠派发实验在 74 台、592 张卡上完成 1184 个配对，完整工作吞吐中位数为串行派发的 1.029797 倍。新实验固定原重叠派发和真实依赖计算，比较一次 761856 字节 D2H 与同一条 copy stream 上连续两次 380928 字节 D2H。两块使用同一对锁页主机和设备缓冲区的相邻地址，单独绑在原 186×1024 BF16 投影输出大小的边界。

两臂保持同一组图、计算流、copy stream、每流事件窗、双同步、总传输字节、完整 BF16 和 CPU 校验、收发端 256 字节红区及内存门槛。设置阶段单独校验两种拷贝布局。正式计时中，传输调用数由独立报表核对为每个完整单元一次或两次。四个同卡配对窗口按单拷贝、两块、两块、单拷贝执行，第五个共同窗口采用原单拷贝。耗时与收益以各实测窗口为准。跨节点同步与全量占用需要独立时钟和驱动证据。

根协调者发布精确源码与认领后，通过本目录的 `launch.ship(publication, snapshot, transport, requested=None)` 提交。延用原账本的两个父作业、分组、优先保护、每步最多四台、单机 12 CPU/64 GiB/8 DCU、分片协作停止与时限。最多 74 台和 592 张卡，实际选择以同一次鲜活整机准入和事务预留为准。目标入口位于 `R/incoming/O01-BF16-dependent-d2h-chunks-fleet-v1-93c5218eea4e4f1d8a246ba7583dac85/controller.py`。用 `--reconcile` 读取唯一原作业，独立清场后再释放预约。终态不明时仍保留预约。

运行 `python -I -S -B derive.py` 核验从原源码重建的精确字节，运行 `python -I -S -B check_local.py -v` 验证实际队列逻辑、两种指针布局、同流顺序和坏证据拒绝。该组件范围用于判断同一复制工作内调用粒度对实际耗时的影响。模型和在线性能由各自用例验收。
