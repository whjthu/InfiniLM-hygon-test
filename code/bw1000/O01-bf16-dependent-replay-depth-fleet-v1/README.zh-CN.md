# O01 成批回放深度 3 与 9

挂接原本可用的两个 Slurm 父作业 1087656、1103606，按原节点账本和区域分片。每步最多四台，节点资源为 12 CPU、65536 MiB、8 DCU。历史 f11r4n09/f11r4n10/f11r4n19 原请求及 f11r2n15/f12r2n12 的非项目 KFD 占用继续保留。共享队列的在途预约、就绪更高优先级放置、原意图和新鲜 PCI/KFD/PID、Slurm 手续同时守住当前保护。最多 75 台、600 卡、31 步、3000 个测量臂、36000 个驱动读数。实测分母随实际选中节点和已完成部分保存。

原 32 卡 .797/.816 的 64 个测量对显示深度 3 的有效行吞吐中位数是深度 1 的 2.942 倍，同口径局部驱动忙碌率从 34.03% 到 67.34%。每完成一对依赖链的主机提交、同步等待和事件查询分别从约 100.35、62.75、19.89 微秒降至 27.85、55.23、5.10 微秒。同步期间 GPU 可以工作，主机时间和 GPU 事件区间可能重叠，因此这些读数无法直接给出设备独占空闲时间。

本轮每个卡保持相同驻留输入、投影和完整消费者，比较同一卡的 3、9、9、3 四个固定 60 秒窗口。每个逻辑对含两条 BF16 D2D 拷贝、V 投影 M186/K4096/N1024 和 8×186×128 的因果概率×V 依赖链。每种深度均捕获两种起始符号，实际相邻回放交换符号，两臂的逻辑输入正负顺序相同。捕获后反转同地址输入，通过两个连续的回放重新核对完整投影、CPU 前 16 列及全量 CPU 消费者输出。按完整回放、逻辑对、投影和消费者次数、有效行和 D2D 字节留数。准备期另记分阶段事件、捕获和首次回放，正式臂保留墙钟、主机提交、同步等待、事件查询和 GPU 事件包围时间。此代理算子结果只作为训练或推理入口后续独立验证的依据。

以原 epoch 加 0/20/40 秒开放三批准备，加 82/108/130 秒分别进入首个有用窗口。原实测通过的 .797 节点所在分片优先，历史有启动超时证据的分片进入最晚一批。第五个窗口在原 epoch 加 397 到 457 秒复用深度 9 图。worker、Slurm、控制器分别使用 480/505/545 秒原预算。节点保留活跃区间及合格驱动读数，独立 clock 读取器只在报告与全部原节点、步骤、时钟误差和读取区间均绑定后才给出共同持续时间、实测分母和采样时差上界。未取得独立时钟证据时仅解释本地读数。固定规模上限预留了 40 卡，因此无 640 卡全池结论。

根协调者发布精确源及认领后，用 launch.ship(publication, snapshot, transport, requested=None) 传入一次新鲜准入和授权传输。指定 requested 时要求原请求集合全部合格，无自动替补。未知原请求仍由同一目标 controller.py --reconcile 对账。高优先级需要回收时 --inspect-stop 只能确认原编号步骤的协作停止入口，终态与独立清场闭合后才 release。
