# O01 零卡 FD 可见性对照

本诊断选取仍在运行的 `.2296` 原八卡保底工作进程。原 `.2297` 两点见证和原 `worker.json` 的固定 SHA 锁定目标。诊断步骤在同一节点核实实际 Slurm 步骤、单核亲和、零 GRES、同 UID、同启动时间、同 cgroup、同 boot 和 `listpids`。采样结束后再次核对原进程仍在该步骤内。

宿主与容器各进行一次只读检查。容器复用 `.2292` 的 DTK sandbox、Apptainer 版本、`--rocm`、`--no-home` 与只读 hyhal 别名绑定。额外只读绑定单个诊断脚本，只启动标准库 Python。该进程不会加载原训练运行时、模型、硬件库或调用设备。诊断只枚举已绑定工作进程的 FD 和读链接分类，不打开任何 FD 指向的文件，也不记录链接目标、进程号、boot 标识或 cgroup 原文。KFD 和 DRM 只检查已知八 PCI，以及 KFD 可见列表是否仅含已绑定进程。出现拒绝、缺失或竞争时保留负面状态，全部结果都无法充当清场证据。

`probe.srun_argv(probe.STAGE / 'probe.py', source_sha)` 渲染唯一目标 argv。采用前须普通发布、核对目标文件 SHA、确认 `.2296` 仍以原资源运行、原 label 与输出目录均未出现，然后在原允许的控制入口内持久化一次性调度意图并执行。最终从独立 Slurm 账务核验诊断真实资源和终态，再消费小型 JSON。未验证目标 DTK 下 `/usr/bin/python3` 与 256 MiB 限额的实际启动。如启动失败，保留失败，不自动提高资源或重复提交。

这次仅检查 `.2296` 的一个已知工作进程。它可以验证当前环境的宿主与容器可见性差异，无法识别原 `.2292` 发生权限拒绝的具体进程，也不放宽原来的全范围设备持有者检查。它不触碰原补位保护、预算或释放回执。
