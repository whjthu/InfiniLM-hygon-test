# O01 BF16 依赖回放深度 9 与 15

原 600 卡实测中，depth9 的同卡有效行吞吐中位数比 depth3 高 46.24%，局部驱动忙碌率为 94.64%。每个已完成逻辑对的主机提交约 10.06 微秒、事件查询约 0.95 微秒、同步等待约 72.50 微秒。同步等待与 GPU 活动可以重叠。若每次回放的提交和查询成本近似固定，9→15 只可能摊薄约 4.4 微秒/对的这部分开销。它是便于核验的局部假设，忙碌率和时间片都无法提供严格的吞吐上界。试验只利用闲置 O01 节点，训练和推理排在前面。

在原四个代表节点使用同一进程的两个回放深度，测量顺序为 9、15、15、9，每臂 30 秒。每个逻辑对有两条相同的 BF16 输入 D2D 拷贝、M186/K4096/N1024 V 投影和 8×186×128 因果概率×V 消费链。`dependent.py` 使用原600卡代码的原字节。两臂使用同一驻留输入、权重、投影、消费者和原 PCI 种子，保持正负逻辑调用次序并做捕获后同地址异值验证。独立读取器核完整 BF16 投影、CPU 前 16 列及完整 CPU 消费者、完整臂、并行测量边界和实际 HIP provider。

有效行/秒用每臂完整墙钟与实际完成行数；驱动忙碌率单列在每臂六个有效读取点。报告还保留每种深度的两个实际捕获与首次回放的耗时、准备阶段、主机提交/同步/查询、事件包围区间以及显存边界。显存快照观察两种图共存后的余量。单独 depth15 的分配峰值和 GPU 独占耗时仍未知。不同节点的时钟与相同活动区间未做独立约束。

32 卡、128 臂、64 对、768 驱动读数任一不完整时不晋级。完整后仅在以下同时成立时保留组件候选：有效行吞吐比所有对中位至少 1.03，两种配对顺序和每个节点的中位均至少 1.01，至少 48 对在一个测量臂所完成的逻辑对数以内摊回额外捕获开销。未达到门槛保留 depth9，结束本参数轴。通过后仍须真实调用方单独验证，本次对照不自动扩到其他节点。

## 一次启动和原请求对账

四个固定节点为 1087656 的 f12r3n17/f12r3n18 和 1103606 的 f12r2n10/f12r2n13。仅各两节点全部通过 CPU-only 新鲜独立 PCI/KFD/PID、Slurm 账单、共享队列已在途/优先就绪保护后才进入。每父独立一个 step，各节点 8 DCU、12 CPU 和 65536 MiB。worker 和 HOST 控制器共用同一 epoch，绝对截止分别为 +260 和 +325 秒，Slurm 步时限为整五分钟。两父的准备开始偏移为 0/20 秒，首个测量臂为 82/112 秒。现场第二次检查发现任一已知资源冲突时不启动两个 step。未知提交结果保留队列原句柄。

根协调器普通发布 `SOURCE_FILES.json` 的所有源码及 `ROOT_CLAIM.json`，并验证 `package.py` 和 `launch.py` 的原证据、现场调度和队列依赖。将已授权 transport 和实际 fresh snapshot 传入 `launch.ship(publication, snapshot, transport)` 一次。需要明确 `requested` 时只接受原四台。`SOURCE_FILES.json` 的目标 members 包括 `controller.py` 及它的 worker/report/scope/decision；旧终态与 T01 证据供根端核验。
