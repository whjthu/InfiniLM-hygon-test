# Graph64 v4 持续前向投影对照

使用 T01 `decoder_06.v_proj` 实际出现的 BF16 M186/K4096/N1024 形状，对照零填充后的 M192。两臂都回放 64 个 GEMM 的 HIP graph，使用共享权重及两组有效行相同的确定性合成输入。每臂核对完整有效行、CPU 计算的前 16 列和 padding 零值。原 T01 真实 VJP 实验的 padded/native 中位耗时比为 1.712，梯度路径继续保留原行。这次检验的是持续前向回放受行对齐及 padding 影响的程度。

以已清场的 v3 48 卡结果作为设置与计时方法基线。v3 的 M184、短窗口和 graph/eager 比值各自封存。v4 单次启动后 +60、+124、+188、+252 秒开始 ABBA 四个窗口，各持续 60 秒。绝对设置截止在首臂前 2 秒，各臂就绪截止在其开始前 200 毫秒。worker 硬截止 +330 秒，编号 Slurm 步上限 345 秒，原控制器截止 +385 秒。先报告有效 186 行吞吐和同卡配对比，再分别报告实际执行行、填充行、完整图回放数和四个 15 秒区间的完成数。每臂每卡 12 个固定驱动采样点，实际样本单列。

最多覆盖原 75 台、600 卡。五台原受保护节点继续排除。派发只接受新鲜 Slurm、PCI、KFD、PID 回执与共享队列认领，高优先级训练和推理保留原位置。默认使用所有符合条件的整节点，也可明确传入较小集合。分片按父作业和区域分组，最多 4 台一片。

根协调者发布源码后调用 `launch.py:ship(publication, snapshot, transport, requested=None)`。如需让位，先用原控制器 `--inspect-stop LABEL SHARD_REQUEST STEP` 核原请求、同父同区布局、运行中 numbered step、发行进程及各节点 worker intent。入口只输出经查证的单个 `scancel --signal=USR1 PARENT.STEP`。根决定是否执行并重新核验。worker 在完整回放之间检查停止请求，结束后保存已核实的部分臂和缺失分母。需取得实际 Slurm 终态及同父独立 PCI、KFD、PID 清场才释放节点。回执缺失时保留原预约。

全选分母为 31 个分片、75 台、600 卡、2400 个卡臂和 28800 个驱动卡采样点。实际分母由原计划冻结。吞吐与驱动利用率限于此组件及固定活跃窗口，不能用于推理用户速度、模型质量或全 640 卡持续利用率验收。
