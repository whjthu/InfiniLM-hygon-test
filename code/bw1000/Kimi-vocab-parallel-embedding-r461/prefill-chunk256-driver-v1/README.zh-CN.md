# Kimi TP32 的 256-token 预填充候选

原 r461 `.643` 在四节点全部加载并通过 4 GiB 驱动空闲显存下限后，第一次 512-token 预填充窗口内低于下限 282 MiB，完成请求数为零。该窗口也包含编解码、重置、调用和边界等待，现有记录没有给出某个算子的独占峰值。

本包以原 `full-model-v4` 的 TP32 C1 调用路径为基础。配置必须显式给出 `prefill_chunk_tokens=256` 或 `512`，四个节点在调用加载器前交换该值，发现不一致就停止。对同一完整输入，256 候选会多做预填充调用，保留连续的绝对位置和已提交上下文，仍只在消费完整输入后发出首 token。固定的 32768 上下文、4096 生成上限、自然 EOS、单 token 解码与显存下限沿用原路径。每个请求记录分块设置和实际预填充调用数。

原源几何下，512→256 将单个 BF16 残差或归一化张量的逻辑尺寸从 63 MiB 降至 31.5 MiB，单个 F32 投影输入从 126 MiB 降至 63 MiB。这些尺寸来自源码，分配器复用、驱动峰值和隐藏工作区仍待实测。多一次预填充调用还会多准备 320 KiB 的 BF16 logits 宿主缓冲并经过原对齐和同步路径。分块可能增加首 token 时延。

本机测试用真实 NumPy 和 ctypes 记录类型化调用的字段。两种宽度分别覆盖 8 个输入长度，最大完整输入为 28672 token，另保留 4096 生成预算。覆盖四节点分块值冲突、非法宽度、首块 guard 失败时的重置和逐位置连续性。数据是本机生成的整数，实际算子、显存和模型输出均未执行。

只有在原 Native 及因果 KV/位置接口数值核验、配对输入、显存采样和原时钟闭合后，才能冻结真实目标运行。当前包仅提供两个候选调用文件、测试和来源证据，运行配置与 Slurm 启动入口另行绑定。
