# 在原保底自然结束后派发 Z-Image 八卡见证器

固定在父作业 1103606 的 f12r2n11，复用原 e23d24ea0c9c4d00af06154d82dc22e8 请求和已发布的原生库。启动器保留原前置、GPU、后置顺序，并分别使用已冻结的步骤标签。原 .2075 在近期实际观测中仍为 RUNNING。24 GiB 请求预算与节点内父作业的 240,000 MiB 分配已在 Slurm 核对，实际步骤内存水位随运行归档。

从本工作树用 `render.py` 渲染 18 个 HOST 文件及 manifest，包含固定运行时、独立准入脚本、保底守卫和原零卡佐证。由 `transport.py` 在既有配置和主机 pin 下做一次部署。部署只编译 Python AST 并校验字节。连续操作共享同一个 manifest SHA。

1. `observe` 用实际 Slurm 读取父作业、编号步骤和账务，并对账已经落盘的宿主、容器及监督器收据。
2. `reserve` 在现有保底锁内核对真实旧步骤并原子固化预约。保底调度在同一锁内使用带守卫的桥接器。监测器同时明确保护该节点及原 .2075。
3. `pre` 要求旧步骤实际 COMPLETED 0:0，再以独立零卡步骤收集八个 PCI、boot 和设备持有者。新阶段使用相同且可验证的预约 SHA。
4. `gpu` 对账实际零卡终态，核对原 boot 后只提交一次八卡、12 CPU、24 GiB、240 秒步骤。原就绪和终态由步骤号、归属和监督器收据核对。
5. `post` 要求该编号 GPU 步骤真实终结，独立清场后生成唯一普通八卡保底授权。外层监测再用授权请求补位并消费同 PID 的真实八卡计算增长。

阶段先写独占 intent。传输观察失败保留原 intent，随后使用 `observe` 和实际原编号对账。此次预注册是单卡算子见证和七张并行保底的八卡节点交接，正式配对性能另行安排。

`handoff` 在同一次共享锁内按顺序调用 `pre` 和 `gpu`，减少两次登录之间的空窗。前一阶段独立 Slurm 终态与原收据仍须通过。已存在前置 intent 时继续核原编号。
