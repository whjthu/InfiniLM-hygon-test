# Git-only 协作流程

## 分支与目录

`main` 是小型共享账本与交接入口。`bw1000-experiments` 和 `bw1100-experiments` 是各自实验代码线；同一优化需要独立比较时再开能说明内容的分支。每边使用自己的 checkout/worktree，不同时改同一个工作目录。

```
coordination/tasks/                 任务归属与合作关系
status/bw1000/latest.json           仅 BW1000 agent 更新
status/bw1100/latest.json           仅 BW1100 agent 更新
code/<hardware>/<experiment>/      可审阅源码快照或补丁
results/<hardware>/<date>/<id>.json 不覆盖的实验记录
analysis/<hardware>/               分析和负结果
handoff/                           接入与迁移材料
manifests/                         依赖、源码、产物 SHA
archives/                          已发布历史基线
```

## 每轮流程

1. **同步**：fetch，两边读协议、任务、最新 status 和上轮结果。不要只看聊天总结。记录本轮消费到的对方 commit。
2. **认领**：先判断是实现新方法、移植已有方法，还是独立复测。认领文件写 owner、方法、模型、代码基线、硬件、资源范围、预期能区分的问题、相关任务。普通 push 成功后再启动昂贵工作。
3. **并行**：各自工作分支提交代码；跨硬件合作通过 commit/cherry-pick 或确定 SHA 的补丁，不复制正在修改的工作目录。代码必须能映射到对应结果。
4. **测试**：同硬件先做基线/候选配对；一次加载跑多个测试。冷加载时间、prefill、decode 和客户端延迟分别记录。跨硬件比较需对齐模型、权重、精度、工作负载和服务体验要求；硬件相关路线可分开。
5. **封存**：把通过、失败、无显著收益都存成新结果文件。运行中、组件合格、模型合格、在线合格是不同状态；附真实句柄和原证据 SHA，不把未完成结果晋级。
6. **汇总**：各自更新自己的 status，并将结果/交接材料合入 main。另一边下一轮 fetch 后复用结论；改进被另一边采用时记录采用的 commit 和独立验证结果。

## 认领冲突与去重

同一实现路线使用同一个语义任务名，例如 `implement-vocab-parallel-head`。任务文件用 Git 版本记录归属变化。两边同时新增同名任务时，普通 push 只有一个能先成功；后提交者 fetch/rebase 后看到冲突，应保留先到的认领并转为合作验证，不强行覆盖 owner。

不同硬件分别验证同一路线不算重复实现。实验去重键至少包含：方法/源版本、模型与权重标识、硬件、精度、TP/PP/EP、输入输出/到达轨迹、microbatch、驻留上限及关键 flags。最后观测过旧不代表任务已死；先查实际句柄或让对方通过仓库状态交接，再转派。

每方只修改自己的 status。结果文件不覆盖；修正分析另存新版本并引用 `supersedes`。每次代码或方向改变、测试终结、出现可复用瓶颈时都更新；开始下一轮昂贵实验前必须读取对方更新。无需不停地提交未改变的轮询记录。

## 大文件与最终交付

小型 JSON/CSV、分析和压缩源码归档可直接 Git 管理。模型权重、原始激活、数 GB trace 不进入 Git，保留在实验存储端，通过 manifest 记录 SHA/大小/访问范围；有用的汇总数据仍放本仓库。

优化完成后先固定各硬件通过验收的版本，再开 `delivery`：整理源码、必要测试、运行说明；从交付树移除 `coordination/status/results/analysis/archives` 等实验目录。保留当前实验分支和提交历史以便复现；无需 force-push 或历史清理。此时再决定把干净代码交给正式项目，按用户后续授权执行。
