# Astra 周期优化审核

用户要求加快真实性能迭代。本约定约束 BW1000 后续执行；BW1100 可采用相同节奏，并在自己的 status 中确认。已有审核与原证据继续复用，不重做一套流程。

## 触发方式

- 全局累计完成 **3 轮有区分力的优化/因果实验**，启动一次 `gpt-6-astra` 审核；不同模型的轮次可以合计，不等每个模型都测完。
- 同一路线连续 **2 轮无实质收益**，提前审核；不因再做一次相同微小收益重复试验而归零。
- 同一路线 **90 分钟没有可测候选或新增因果证据**，在下一次结果处理、任务派发或协调者恢复执行时提前审核，检查是否应修复最小阻塞或转替补。加载、排队、编译、审批/等待、实际计算时间分列；90 分钟不是自动取消作业的授权。
- 反复出现可避免的测试脚本/加载器/审计错误时提前审核；这些失败不算性能轮次。
- 严重数值回归、性能倒退或关键证据互相矛盾时立即审核。用户直接要求时立即启动，不等计数。

一轮指一个明确假设的配对性能试验或能排除关键原因的诊断。一次加载的多个 arm、多个 batch 点合为该轮。负结果同样计数；轮询、写清单、重复编译、无新增信息的重测不算性能迭代。纯 CPU/编译通过只能列工程进展，不能当成性能收益。

同一时刻最多一个此类周期审核。在途时将新增结果加入待审队列，不重复创建；确需补充时给已有审核者发增量证据。审核期间，独立且已具备执行条件的实现/测试继续，不让所有 agent 等评审。

## 每次审核必须回答

1. 最近几轮整模型/真实服务提升了多少？哪些只是组件、编译或控制协议进展？对比是否同硬件、同负载、同计时口径，收益是否超过波动？
2. 时间花在哪里：加载/排队/准备/反复校验/等待，还是实际 GPU 试验？是否存在有资源但无可测任务，或报告很多却没有性能结果？
3. profile 对应当前负载吗？瓶颈是计算、专家负载、通信、同步/空泡、CPU 调度还是数据搬运？分清已证实、假设与未知，不用硬件大 GEMM 峰值直接预测小 batch 性能。
4. 哪些路线保留、停止、转替补？逐模型最多 2 张下一步实验卡，并按潜在整模型收益和得到首个结果的耗时排序。

每张卡写：一个待证伪假设、一个最小改动、owner/资源、复用的源码/证据、必要数值检查、足够判定的预热后样本、预期能影响的 wall 区间或 UNKNOWN、退出/升级条件和替补。先做最短路径的实际判定；只在组件显示有价值后才支付完整模型加载/验收成本。

每张卡还应给出取得首个可判定结果的预计耗时，并在结束时记录实际准备、排队、加载、测量、质量检查耗时。按潜在整模型收益与取得结果的时间排序；证据不足时写 UNKNOWN，不用组件倍率代替收益预测。审核不得新增与本次判断无关的构建、门禁或报告工作。

## 审核后必须执行

协调者逐条登记 **采纳/拒绝/暂缓及理由**，将具体文件、配置、资源和退出条件发给原执行 agent。不能只保存报告。下一次审核首先回看上一轮实验卡的实际结果和未落实原因；证据未变的重复建议直接复用，不另造工作。

同源码/依赖/范围的已通过构建、接口、资源清理和基线证据可复用；一个权重加载尽量完成相关配对。模型晋级仍需完整最终 token/EOS、真实计时和正常退出，不能以组件误差/中间位一致替代；不引入 GPU F64。故障未知执行不能自动重播，资源隔离和其他人的作业边界不变。

## 记录与 Git 协作

各端保存自己的轮次事件与审阅状态；共享入口为 `coordination/reviews/<hardware>/latest.json`，审核及落实结论放 `analysis/<hardware>/reviews/`。用真实实验/句柄去重，记录已审轮次、待审轮次、审核 agent/model/开始时间、结论及落实证据。未完成审核标为 RUNNING；不把启动当成完成。

审核结论、优化方向调整及实验终结是实质更新，准备好后及时普通 push。每 10 分钟的 Git 检查仍只负责发现对方更新，不因轮询创建 Astra、编造新轮次或上传空心跳。
